## 왜 나눴나 (2026-10-29)

한 파일(`decisions.md`) 끝에 모두가 D-번호를 붙이다 보니 같은 번호를 두 사람이 쓰고(D-018), PR마다 같은 줄에서 충돌이 났다. 파일을 담당별로 나누고 번호도 파일마다 따로 매기면(A-001, B-001…) 서로 같은 줄을 고칠 일이 없다.

## 무엇을 어디에 쓰나

- **회의에서 정했다 / 다른 담당 코드도 바뀐다** → `decisions-team.md`에 T-항목. 방향·목표가 바뀌면 `direction.md`도 같은 PR에서.
- **내 담당 안에서만 바뀐다** → `decisions-<내 담당>.md`에 내 번호로.
- **다른 담당이 해야 할 일** → GitHub 이슈 (라벨 `담당-A/B/C`). 남의 결정 파일을 고치지 않는다.
- **예전 D-결정을 바꾼다** → 새 파일에 항목을 쓰고, `decisions.md`의 그 항목 상태 줄 끝에 "→ T-001로 대체"처럼 한 줄만 붙인다.
- **밸런스 숫자** → md에 적지 않는다. 원본은 코드 설정(`src/shared/Config/*.luau`)이고, md에는 목표만 (`direction.md` "숫자는 어디에").

## game-design.md 섹션 담당

| 섹션 | 담당 |
|---|---|
| 게임 소개, 핵심 루프, 개발 방식과 로드맵 | 팀 (회의 뒤) |
| 광산 구성, 화면 예시 중 채굴 화면 | A |
| 도파민 장치와 광물 도감 | A·B (가격·도감 B, 광물·연출 A) |
| 차별화: 광맥 붕괴 이벤트 | C (연출은 A) |
| 수익 모델 | C |
| 팀 역할 | 팀 |

자기 섹션이 아닌 곳을 고쳐야 하면 이슈로 요청하거나 PR에 그 담당을 멘션합니다.

## 기획을 바꾸는 방법

1. 브랜치를 만들고 위 규칙대로 결정 파일과 기획서를 고칩니다.
2. 바뀐 기획 때문에 코드·맵을 고쳐야 하면 PR 설명에 적습니다.
3. PR을 올리고 영향받는 담당을 멘션한 뒤 직접 머지합니다 (D-015).

## AI 에이전트에게

- 기능을 구현하기 전에 `direction.md`와 관련 결정 파일(team + 자기 담당)을 먼저 읽습니다. 예전 결정은 `decisions.md`.
- 충돌하면 우선순위: `direction.md` > `decisions-team.md` 최신 > 담당별 결정 최신 > `decisions.md` > `game-design.md`.
- 사용자 요청이 방향·기획과 다르면, 구현하기 전에 그 차이를 알리고 문서를 고칠지 묻습니다.
- 결정은 사용자 담당 파일에만 씁니다. 회의 결정이라고 사용자가 말하면 `decisions-team.md`에.
- 기획에 없는 숫자(확률, 가격, 시간)는 임시값으로 구현하고, PR 설명에 "임시값"이라고 적습니다.
